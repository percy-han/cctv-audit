# 门店 CCTV 视频智能稽核 Agent

给一个视频地址，Agent 打开页面、连续采集画面、按时间窗口切片，用 Gemini 原生视频理解逐窗口比对门店 SOP，输出**带证据帧**的违规清单。

面向几小时长度的门店录像设计：**上下文占用与视频总时长无关**，稽核结果准实时上屏。

---

## 一、它是怎么工作的

```
┌─ Navigator ─────────────────────────────────────────────┐
│ 确定性 Playwright：登录 / 打开目标 / 跳时间 / 起播        │
│ 每个平台一个适配器（当前：bilibili + 通用兜底）           │
│         ↓ 选择器失效或页面陌生时                          │
│ Gemini Computer Use 兜底（仅做导航，不做稽核判定）        │
│         ↓ 遇到验证码 / OTP 时                            │
│ 人工介入闸门：大屏弹横幅 → 人处理 → 点「继续」            │
└──────────────────────────────────────────────────────────┘
                          ↓
┌─ Capture ───────────────────────────────────────────────┐
│ Plan A 抓流：截获播放器自己的 HLS/FLV/DASH 请求，          │
│              带着页面的 Cookie/Referer 用 ffmpeg 直拉      │
│ Plan B 录屏：CDP screencast → ffmpeg → MP4（万能兜底）    │
│ 启动时自动探测，产出重叠的 W 秒窗口 MP4                    │
└──────────────────────────────────────────────────────────┘
                          ↓ 有界队列（满了对采集施加背压）
┌─ Analyzer ──────────────────────────────────────────────┐
│ N 个协程并发。每个窗口一次**全新无状态**的 generate_content │
│ 视频 Part + response_schema → 结构化 JSON。不传任何历史    │
└──────────────────────────────────────────────────────────┘
                          ↓
┌─ Store ─────────────────────────────────────────────────┐
│ 唯一落盘入口：JSONL 一行一窗口 + 每条违规抽一张证据帧 JPG  │
│                          ↓ 推送                          │
│ 实时大屏（另一个进程）                                    │
└──────────────────────────────────────────────────────────┘
```

### 为什么是这个架构

上一版是「一轮一张截图，让模型描述 10~15 秒区间」。25fps 下时序覆盖率约 **0.27%**，而 5 条 SOP 里有 4 条是**缺失类**判定（未洗手、未冲洗、未加盖、看手机）——**缺失类命题在单帧上不可证伪**。旧产物里已经出现从单帧推出的 31 秒否定结论（"在没有进行任何搅拌操作"）。

改成原生视频 1 FPS 后，**覆盖率 ×10，token 成本持平或更低**：

| 方案 | 1 分钟看到的帧数 | 大致 token |
|---|---|---|
| 旧：1080p PNG × 4-6 轮，历史留 2 张 | 4–6 帧 | ~18k |
| 新：原生视频 `MEDIA_RESOLUTION=low` 1 FPS | **60 帧** | ~6k |
| 新：原生视频 `MEDIA_RESOLUTION=high` 1 FPS | **60 帧** | ~18k |

另一个关键点：**浏览器操作和视频稽核是两次不同的模型调用**。旧版把两件事挤在同一个 loop 里，是所有 P0 问题的共同根源。

### ffmpeg 在这里干四件事

系统级依赖，不是 pip 包。`apt install ffmpeg` / `brew install ffmpeg`。

1. **拉流**（Plan A）：带着页面的 Cookie 和 Referer 去下载 m3u8
2. **切片**：`-f segment`，每 `step` 秒吐一个 MP4，就是流水线的生产者
3. **合成**（Plan B）：`-f image2pipe` 从 stdin 收 CDP 截屏帧，编码成 MP4 ——**它是「一堆散图」和「一段视频」之间的桥**，覆盖率 ×10 的收益全靠它
4. **抽证据帧**：`ffmpeg -ss <t> -frames:v 1`，把违规时刻定格成 JPG

### 快在哪、不快在哪

- **Plan A 抓流**：不"播放"视频，按带宽下载分片。**只有回放/录像能超实时**（几小时录像常可几分钟拉完）。若目标是**实时直播流，抓流同样只能是实时速度**——数据本身就按实时产生。
- **Plan B 倍速**：录屏只能跟着画面走，`PLAYBACK_RATE=4` 可把 3 小时素材压到 45 分钟。代价是快放丢帧、动作发糊，平台倍速上限通常 2x–8x。窗口时长会自动按倍率换算，`WINDOW_SECONDS=15` 始终是 15 秒**视频内容**。

## 二、快速开始

```bash
# 1. 系统依赖
sudo apt install ffmpeg          # macOS: brew install ffmpeg

# 2. GCP 鉴权（不需要 API Key）
gcloud auth login
gcloud auth application-default login
gcloud config set project <your-project-id>

# 3. 配置
cp computer_use_agent/.env.example computer_use_agent/.env
# 至少填上 GOOGLE_CLOUD_PROJECT —— 代码故意不设默认项目

# 4. 启动（首次会自动建 venv、装依赖、装 chromium）
./start_web.sh
```

- 💬 对话控制台：`http://127.0.0.1:8000/dev-ui/`，选 `computer_use_agent`
- 📺 实时大屏：`http://127.0.0.1:8080/`

在对话框里直接给地址即可，稽核区间写在同一句话里：

```text
稽核 https://www.bilibili.com/video/BV1GJ411x7h7 第1分钟到第5分钟
稽核 https://www.bilibili.com/video/BV1GJ411x7h7 前三分钟
稽核 https://www.bilibili.com/video/BV1GJ411x7h7 从 12:30 开始看十分钟
稽核 https://www.bilibili.com/video/BV1GJ411x7h7 一分半到两分十秒
```

**这句话是交给模型读的，不是关键词匹配**（`intent.py`）。所以不必按格式写，说人话就行；
`第1分钟` 按 **01:00 这个时刻**理解，不是"第一分钟这一整分钟"。开跑第一行会把模型的理解
回显成 `01:00 → 05:00` 外加一句「我的理解：从 01:00 看到 05:00」，读错了当场就能看出来。

不写时间就是整段视频。**但说不准的时间会直接停下来问你**——比如「看最后五分钟」，
不知道录像总长就换算不出秒数，这时候宁可停，也不会默默按"整段视频、从头开始"跑掉
（那是最贵也最可能错的一种猜法）。

模型只从这句话里读**三样东西**：地址、起点、终点。回复的结构里压根没有放规则的地方，
所以哪怕你在对话框里写满检查项，也一条都进不去——稽核标准的唯一来源是那份 YAML。
连不上 Vertex 时会退回旧的关键词解析，横幅里会明说，那时它只认得少数几种写法。

## 三、配置

全部配置项见 `.env.example`，几个要点：

| 配置 | 默认 | 说明 |
|---|---|---|
| `WINDOW_SECONDS` | 15 | 分析窗口（视频秒）。改成 600 做 10 分钟长窗口也可以 |
| `WINDOW_OVERLAP_SECONDS` | 3 | 窗口重叠。跨边界的动作（"拿了手机又摸杯口"）若被切飞，两侧窗口都看不见 |
| `CAPTURE_MODE` | auto | `auto` 探测；`stream` 强制 Plan A；`screen` 强制 Plan B |
| `MEDIA_RESOLUTION` | low | low ≈ 66 tok/帧，high ≈ 258 tok/帧。判"有没有戴蓝手套"这类细节要用 high |
| `FULLSCREEN_PLAYER` | true | 让播放器铺满视口再录，画面细节是真的变多，不只是没被裁掉 |
| `CROP_TO_PLAYER` | true | 裁掉页头/侧栏，以及全屏后播放器内的黑边（竖屏视频在 16:9 视口里三分之二是黑的） |
| `STOP_ON_VIDEO_END` | true | 播完的 `<video>` 会一直定格最后一帧，不停会一直计费录空窗口 |
| `SOP_RULES_PATH` | analyzer/sop_rules.yaml | 稽核标准文件。相对路径按仓库根目录解析 |
| `ANALYSIS_CONCURRENCY` | 3 | 并发分析的窗口数 |
| `PLAYBACK_RATE` | 1 | 仅 Plan B 有效 |
| `MAX_WALL_CLOCK_SECONDS` | 3600 | 硬停止。另有 `MAX_COST_TOKENS` / `MAX_WINDOWS` |
| `AUTH_STATE_DIR` | ./auth | 登录态存放处，**内含实时会话 cookie** |
| `HUMAN_GATE_MODE` | auto | 遇到真验证码时是否等人。`auto` 探测大屏活着才等，`wait` 一律等，`off` 立刻失败。Agent Engine 上没人能应答，`auto` 会立刻报错并说明缺什么凭据 |
| `MONITOR_REPLAY_HISTORY` | false | 大屏是本次运行的实时视图。开了会把整份历史记录（可能是按另一套 SOP 判的）在启动时回放进去 |
| `PREVIEW_FPS` / `PREVIEW_WIDTH` / `PREVIEW_HEIGHT` / `PREVIEW_QUALITY` | 15 / 960 / 540 / 60 | 大屏预览走**独立的第二路 screencast**，调它不影响判定画质，也不会拖慢分析 |

SOP 规则外置在 YAML，改规则不用改代码，**这也是稽核标准的唯一来源**——对话框里写的 SOP 不会生效（只解析 URL、起始时间、时长）。每条规则的 `detection_type` 区分 `presence`（看到了才算违规）与 `absence`（整个窗口都没看到才算违规），后者必须 `requires_full_context: true`。

仓库里目前有两份标准，用 `SOP_RULES_PATH` 切换：

| 文件 | 内容 |
|---|---|
| `analyzer/sop_rules.yaml` | 《亚太稽核远程 CCTV 巡检业务流程》5 条 |
| `analyzer/sop_rules.drink_making.yaml` | 调饮 3 条：加冰顺序、蓝色卫生手套、口罩与帽子 |

YAML 里还可以写 `visual_scan:` 段。它列出模型在下任何结论之前必须先描述的观察对象（"手是肉色还是被包裹？包裹物什么颜色？"），结果写进 `visual_scan` 字段，且在 schema 里**声明在 `findings` 之前**——模型按顺序填 JSON，所以它必须先看再判。这是"没戴手套却说戴了黑手套"那类幻觉的直接对策。

## 四、登录与验证码

**策略是绕开触发，不是硬刚。** 现代滑块（极验/腾讯防水墙/阿里）核心检测的是浏览器指纹而非拖动轨迹，Playwright 默认会被 `navigator.webdriver`、CDP 痕迹、WebGL 指纹识别——缺口找对、轨迹拟人也照样过不去。本项目**不做通用反检测**。

按优先级：

1. **会话复用（首选）**：人工登录一次，`storage_state` 存下来，之后带登录态启动。验证码只在首次出现
2. **持久化 Profile**：指纹稳定，降低被判定为新设备的频率
3. **人工介入闸门**：检测到验证码/OTP → 流水线挂起 → 大屏弹横幅 + 实时画面 → 人远程处理完点「继续」→ 继续跑。企业平台的短信/OTP 走同一条闸门
4. **走正门**：真实客户平台优先申请专用稽核账号 + IP 白名单免验证码。这是商务动作，应先于技术投入

点选式验证码（"依次点击图中的 X"）可交给 Computer Use 兜底层尝试——它本就输出归一化坐标——但成功率不保证，失败即降级到闸门 3。

> bilibili 测试阶段：多数视频免登录可看，**不要投入精力过 bilibili 的滑块**，那是与真实平台无关的工程债。

`auth/` 下的文件是**实时登录凭据**：目录 `700`、文件 `600`、已进 `.gitignore`。

### 登录弹窗 ≠ 验证码

两件事必须分开，否则闸门会天天误触发。实测：bilibili 播到 60–90 秒会弹 `.bili-mini-mask`
登录弹窗，它**会把视频暂停**，而且弹窗里天生带一个图形验证码输入槽（登录表单的一部分），
平时塌成 `0x0`，弹窗可见时量到 559×284。

- **登录弹窗**：`keep_clear` 关掉就完事，播放由卡顿恢复重新拉起。不惊动任何人
- **真验证码**：页面会**用文字说**它在验证你（"请完成安全验证"/"拖动滑块"/"点击图中"）

所以 `detect_challenge` 分两级：厂商专用选择器（`.geetest_panel`、`#tcaptcha_iframe` …）
单独出现就算数；`[class*='captcha']` 这类通配选择器**只在页面文字同时印证时才算数**。
尺寸下限拦不住这个场景——弹窗一可见，那个槽就是全尺寸的。

`_rescue` 在惊动人之前还会先调一次 `keep_clear` 再重测：挡住步骤的遮罩，通常就是探测器
正看着的那一个。

### 生产上没人可以登录

闸门的三条释放路径（大屏「继续」、`resolve()`、验证码自己消失）在 Agent Engine 上一条都
不存在：没有显示器、没有大屏、没人盯着。所以 `HUMAN_GATE_MODE=auto` 会**先探测有没有人能
应答**，没有就立刻失败并指明缺什么凭据，而不是等满 900 秒再报一个超时。

生产上的正解不是这个开关，是让验证码根本不出现：

1. 线下在有图形界面的机器上人工登录一次，导出 `storage_state`，放进 Secret Manager，
   运行时挂到 `AUTH_STATE_DIR`。凭据轮换是运维动作，不是 agent 的运行时行为
2. 向平台申请稽核专用账号 + 出口 IP 白名单，从源头免掉风控。这是商务动作，应先于技术投入
3. 真到了闸门那一步，就当作"这次跑不了"，把缺什么凭据写进报告——比挂着强

## 五、安全须知

- **大屏默认只绑 `127.0.0.1`**。它推的是含**可识别人脸**的实时监控画面。要对外暴露，必须设 `MONITOR_TOKEN` 并挂在带鉴权的反向代理后面
- `/api/event` 和 `/api/interact` 是写接口，设了 token 就强制校验
- 证据帧只从证据目录内提供，路径 resolve 后二次校验，防目录穿越
- 稽核产物（`checkpoints/` 下的记录与证据帧）含真人影像，已 gitignore
- 媒体 URL 的查询串里常带鉴权 token，日志里统一脱敏
- 送进模型的页面文本一律视为**不可信数据**，不作为指令执行

## 六、已接受的遗留风险：Region

`GOOGLE_CLOUD_LOCATION` 固定为 `global`（写死在 `config.py`，不从 `.env` 读）。Computer Use 是预览特性，区域端点会报 "computer use is not supported for this model in this region"。

代价：`global` 意味着请求由 Google 全球负载均衡按容量路由，**无法控制请求落在哪个地理区域处理**。带客户做合规确认时若不可接受，退路是——视频理解层改用普通 Gemini 模型（有区域端点），只有 Computer Use 兜底层受 global 限制。分层设计天然提供了这条退路，主链路不受影响。

## 七、项目结构

```text
cctv-audit/
├── start_web.sh                 # 一键启动：查 ffmpeg、装依赖、拉起大屏 + ADK Web
├── requirements.txt             # 运行时依赖（ffmpeg 是系统依赖，不在这里）
├── requirements-dev.txt         # 测试依赖
├── tests/test_units.py          # 纯逻辑单测：时间映射、窗口切分、结果清洗、id 序列
└── computer_use_agent/
    ├── config.py                # 唯一的配置入口，其他模块不准调 os.getenv
    ├── agent.py                 # ADK 入口：解析指令 → 驱动流水线 → 流式回报
    ├── pipeline.py              # 采集协程 + 分析协程池 + 预算硬停止
    ├── store.py                 # 唯一落盘入口 + 证据帧抽取
    ├── gcp.py                   # 凭据与带重试的 generate_content
    ├── browser_actions.py       # 浏览器原子动作分发（只此一份）
    ├── navigator/               # 确定性导航
    │   ├── base.py              # 协议 + 会话复用 + 验证码探测 + 人工闸门
    │   ├── bilibili.py          # 当前唯一的真实适配器
    │   ├── generic_agent.py     # Computer Use 兜底（仅导航）
    │   └── resilient.py         # 把上面两者缝起来：先确定性，失败再兜底
    ├── capture/                 # 采集
    │   ├── probe.py             # 探测能否抓流 → 决定 Plan A / Plan B
    │   ├── stream_grabber.py    # Plan A
    │   ├── screen_recorder.py   # Plan B
    │   ├── preview.py           # 大屏那路画面（两个 Plan 都跑，与采集无关）
    │   ├── window_assembler.py  # 定长切片 → 重叠窗口
    │   └── ffmpeg_util.py       # ffmpeg 定位、抽帧、URL 脱敏
    ├── analyzer/                # 稽核
    │   ├── sop_rules.yaml       # SOP 规则，改这里不用改代码
    │   ├── sop_rules.drink_making.yaml  # 另一套标准，SOP_RULES_PATH 切换
    │   ├── schema.py            # response_schema，强制结构化输出
    │   └── video_analyzer.py    # 每窗口一次无状态调用
    ├── monitor.py               # 大屏前端页面 + 推送客户端
    └── monitor_server.py        # 大屏服务端（WebSocket 广播）
```

新增一个平台（海康/大华/第三方 SaaS）= 在 `navigator/` 加一个文件，主链路不动。

## 八、内置 SOP 规则

| 编号 | 维度 | 判定类型 | 严重度 |
|---|---|---|---|
| `CHK_ATTIRE_001` | 着装与仪容：工作服、工帽包裹头发、口罩遮盖口鼻 | presence | RED_LINE |
| `CHK_HYGIENE_002` | 手部卫生：接触即食原料/杯口前洗手或戴手套，手套破损即换 | absence | RED_LINE |
| `CHK_TEA_001` | 器具清洁：雪克杯、量杯用后立即冲洗，洁具与食品器具分区 | absence | NORMAL |
| `CHK_SANITATION_003` | 台面卫生：无溢液、积水、茶渣、散落包材，毛巾专用分区 | presence | NORMAL |
| `CHK_BEHAVIOR_004` | 作业纪律：玩手机、脱岗、饮食、在原料上方咳嗽 | presence | RED_LINE |

严重度由规则表决定，模型说了不算——它返回的 `severity` 会被覆盖掉。

| 工作区干净 | 改了没提交 |
| 没有游离文件 | 新写的模块忘了 `git add`——本地 import 得到，别人 clone 下来没有 |
| 没有源码被 `.gitignore` 挡住 | 忽略规则写宽了，源码被静默排除，而本地一切正常 |
| 本地与 GitHub 一致 | 领先/落后几个 commit，或分支压根没推过 |

只读，不替你 commit / push / 改文件。全过退出码 0，有失败退 1（以后想挂 CI 或 git 钩子可以直接用）。

`--deep` 是唯一能证明「**离开这台机器，代码依然完整可跑**」的检查——前六项信的是本机 git 自己的账本，`--deep` 不信，它像陌生人一样重新 clone 一份来核。大改动、交接、开 PR 前值得跑；日常收工用不着。

> 这个脚本存在是因为真出过一次：`git commit` 跑在 `git add` 前面，推上 GitHub 的分支**只有删除、没有新代码**，而本地每一个信号（log 里有 commit、push 成功）都是正常的。

## 十、FAQ

**Q: 大屏没出新卡片？**
先确认 `http://127.0.0.1:8080/` 的 WebSocket 是绿色 `Connected`。第一张卡片要等 `窗口时长 + 切片时长 + 推理时间`（`WINDOW_SECONDS=15` 时约 35 秒，见下面"第一条判定为什么要等这么久"），之后每 `窗口−重叠` 秒出一张。再看 `/tmp/cctv_audit_monitor.log`。

**Q: 报 400 INVALID_ARGUMENT (Computer Use not supported in this region)？**
Location 必须是 `global`，模型用 `gemini-3.5-flash`。见第六节。

**Q: 怎么判断走的是 Plan A 还是 Plan B？换个平台之前怎么先试一下？**

开跑后对话里会打一行「📡 采集方式」，附带选择理由；报告里也有「采集方式」一栏。

想在花钱之前先问清楚一个新平台走哪条路，用这个脚本——它只开浏览器、只探网络，不调模型不花钱：

```bash
PYTHONPATH=. .venv/bin/python tests/probe_check.py <视频页 URL> --all
```

它会把播放器实际下载的每个媒体 URL 列出来，逐个 ffprobe，打印时长和分辨率，最后给出与真实跑批一致的裁决。

要**确认** Plan A 真的跑通了（而不是悄悄退回录屏），用 `CAPTURE_MODE=stream`：探测失败时它会直接报错，不会兜底。

```bash
PYTHONPATH=. .venv/bin/python tests/manual_e2e.py <URL> --mode stream --start 60 --duration 45
```

**Q: 哪些站点能走 Plan A？**

判据不是站点名字，是**能不能拿到一个 ffprobe 打得开、且覆盖整段录像的 URL**：

| 播放器形态 | 结果 |
| :--- | :--- |
| HLS，请求 `.m3u8` | Plan A |
| DASH，请求 `.mpd` | Plan A |
| DASH，manifest 藏在页面 JSON 里，直接 byte-range 一个 `.m4s`（bilibili 就是这种） | Plan A |
| 真·HLS 分片，每个 `.ts` 只有几秒 | Plan B（抓一片只有几秒，没意义） |
| canvas + WASM 解码，网络上根本没有标准媒体传输（海康/大华 web 客户端常见） | Plan B |
| 有 `.m3u8` 但 DRM 加密 / 鉴权头对不上 | Plan B |

bilibili 的 `.m4s` 长得像分片，其实是整段 519 秒的完整轨道。探测器早期按「`.m4s` = 几秒的分片」把它跳过了，所以 Plan A 一次都没真跑过；现在会 ffprobe 它、按时长判断是分片还是整轨，并在多个清晰度里挑分辨率最高的那个。

**Q: 长视频会不会把上下文撑爆？**
不会。每个窗口是一次**全新**的 `generate_content`，不带任何历史。跑 30 分钟和跑 30 秒，单次请求的 input token 是同一条平线。

**Q: 大屏上的画面，就是拿去判定的画面吗？**

看走的是哪个 Plan，大屏的动作横幅会写明：

- **Plan B（录屏）**：是。同一个页面、同一时刻，只是大屏那路降到 960×540 省带宽。
- **Plan A（抓流）**：不是。ffmpeg 独立下载视频并自己定位时间，浏览器只是挂在那里保持鉴权不失效。它的播放进度和正在判定的窗口没有关系——你可能看着第 1 分钟，报告已经在滚第 5 分钟了。

大屏画面由 `capture/preview.py` 单独供给，**与采集方式无关**。这块以前长在 `ScreenRecorder` 里，Plan A 一通，就没人开这路 screencast，大屏直接黑屏——现在它归整个 run 管，不归任何一种采集策略管。

**Q: 大屏画面一卡一卡的？模型看到的也是这么卡的画面吗？**
不是。大屏和分析是**两路独立的 screencast**：分析那路 1920×1080 q85、按 `CAPTURE_FPS` 定时取帧喂 ffmpeg；大屏那路 960×540 q60、按 `PREVIEW_FPS` 走 WebSocket。大屏卡只是观感问题，跟判定质量无关。

卡的原因通常是带宽：一帧全尺寸 q85 JPEG 转 base64 约 280 KB，如果按原样全速转发是 84 Mbps，SSH 隧道扛不住。所以预览单独降到 960×540 q60（约 58 KB/帧），15 fps 只要 7.2 Mbps——比过去 4 fps 发全尺寸帧（9.2 Mbps）还省，却顺畅得多。隧道还是慢就把 `PREVIEW_WIDTH/HEIGHT/QUALITY` 调到 640/360/50（约 27 KB/帧）。发送端有背压：上一帧没发完就丢掉下一帧，不排队。

顺带一提，Chromium 的 screencast **没有固定帧率**——它是每次重绘吐一张，速率 = `min(页面重绘率, vsync 60Hz, 本机 JPEG 编码扛得住的速率)`。实测同一个视频页在 1x 和 2x 播放下都是约 40 fps，暂停后仍有 5.6 fps（弹幕和 UI 在动）。这也是 `_pump_frames` 不直接消费事件、而是自己定时取帧的原因：否则 MP4 的时间轴会跟着 Chromium 漂。

**Q: 报告开头写「⚠️ 稽核提前结束」是什么意思？**
说明实际看过的区间没覆盖到你要求的时间段——报告里的「稽核区间」会同时给出实际值和请求值。多数情况是播放中途卡住：看门狗会先尝试三次恢复播放（对话里出现「⏯️ 尝试恢复播放」），三次都拉不动才停。**未覆盖的时间段既没有通过也没有不通过**，别把"没发现违规"读成"那段是干净的"。

**Q: 大屏老弹「需要人工验证」，我要去哪台机器上开浏览器？**
先看横幅里的措辞。只报一个 `[class*='captcha']` 尺寸、没有引用页面文字的，是**登录弹窗的
验证码输入槽被误判了**——这个已经修掉，探测器现在要求页面用文字印证（见第四节）。真验证码
的横幅会带上页面原话（"请完成安全验证"之类）。真遇上了，答案不是去 agent 机器上开浏览器：
在**你自己**有图形界面的电脑上登录一次，把 `storage_state` 放进 `AUTH_STATE_DIR` 重跑。

**Q: 对话里出现「播放器被弹窗挤出了全屏，已恢复」？**
正常，不用管。采集的取景范围（视口，以及 ffmpeg 的 `-vf crop`，如果有）在录制开始时就固定了，
**永远跟不了播放器**。而页面会移动播放器：实测 bilibili 的登录弹窗会把播放器从全屏
(0,0) 1920×1080 挤到 (62,172) 1354×762，关掉弹窗也不会自己回去。这时录到的就变成页头、
标题栏和**半张画面**；没有裁剪的时候更糟——整帧变成**整个 bilibili 页面**，侧栏推荐评论一应俱全，
真正要稽核的画面缩在一角。而且**什么错都不会报**——帧尺寸照旧，模型照样满怀信心地给出判定。
所以看门狗每 5 秒核一次几何，发现挪了就重新全屏。真恢复不了会打出「⚠️ 裁剪范围已经对不上」，
那时候的结论就别信了。

> 这个守护一度**只在需要裁剪时才生效**：基准几何是跟裁剪框一起记的，而 16:9 的视频全屏进
> 16:9 的视口没有黑边、不需要裁剪，于是基准从来没记下来，看门狗直接跳过。竖屏视频测不出来，
> 横屏视频每次都中。现在基准来自"量过播放器"这件事本身，跟裁不裁无关。

**Q: 第一条判定为什么要等这么久？**
`WINDOW_SECONDS=15` 时约 35 秒：8 秒开页面+全屏+定位播放器，17 秒攒够素材，剩下的是推理。
其中"攒够素材"有下限——**15 秒的片段不播够 15 秒就没法判**。以前是 27 秒，因为切片是按
`步长`（窗口−重叠 = 12s）切的，而 mp4 不关闭就读不了，一个 15 秒的窗口要等两个 12 秒的
切片都关闭 = 24 秒。现在切片按更细的粒度走（默认 2 秒，见启动日志 `... 2.0s segments,
first verdict ~17s in`），下限降到 `窗口 + 切片`。`WINDOW_SECONDS=600` 的收益更大：
第一条判定从约 20 分钟降到约 10.4 分钟。

出第一条之后就是稳态：每 `步长` 秒出一条，落后播放头约 `窗口 + 切片 + 推理` 秒。这个滞后是
结构性的，调不掉——要更快只能把窗口调小。

**Q: 我写了「第1分钟到第5分钟」，为什么从头开始跑、到 5 分钟也不停？**
旧版是 `re.compile` 关键词匹配，只认 `从 12:30 开始` 和 `分析 10 分钟` 两种写法。
`第1分钟到第5分钟` 两条都不匹配，于是起点静默回落到 0、时长静默回落到"无限"——
**两个都错，一声不吭**，还照着整段录像收费。用正则去读人话本来就是错的工具：
现在这句话交给模型读（`intent.py`），说不准就停下来问，不再猜。

**Q: 还有哪些地方在拿关键词猜？**
同一类问题（拿一份写死的清单去匹配一个千变万化的输入，匹配不上就静默回落到默认值）
全仓库排查后清掉了这几处：

| 位置 | 原来 | 现在 |
|---|---|---|
| `monitor.add_video_segment` | 状态串里找 `VIOLAT`/`违规`，都不匹配就当**合规** | 整个方法删了（无人调用，且回落方向正好是最危险的那个） |
| `navigator/generic_agent.py` | 兜底导航是否成功 = 模型的自然语言是否以 `BLOCKED` 开头 | 有客观信号就查客观信号（播放头位置、播放器是否存在）；没有才问模型，并且要结构化的 `{reached, reason}` |
| `navigator/base.py` | 页面出了什么问题，靠一份 bilibili 中文原句清单匹配 | 清单先跑（快且准），**没匹配上就把截图和页面文字交给模型读**，分成 challenge / login / unavailable 分别处理 |
| `analyzer/schema.py` | 模型给的时刻读不出来就悄悄改成 `00:00` | `00:00` 不是空值、是一个具体时刻，证据帧就是照它抽的。现在记录里带 `timestamp_exact: false` |
| `gcp.is_transient` | `"500" in str(exc)` | 看状态码。`15000 token limit`、`gemini-...-0429` 这些以前都会被白白重试三次 |

反过来说，**这几处的字符串匹配是对的，没动**：`.m3u8`/`.flv` 探测（匹配不上就退到录屏，
退路是安全的）、`seg_00042.mp4` 文件名（那是我们自己让 ffmpeg 写的，不是外部输入）。
判断标准不是"有没有用正则"，是"输入是不是开放的，匹配不上时的默认值会不会是错的"。

**Q: 换成海康/大华/客户自己的 SaaS，页面提示语完全不一样，还认得出来吗？**
认得出。`_DEAD_PAGE_MARKERS` / `_CHALLENGE_HINTS` 里的中文原句是从 bilibili 抄的，
在别的平台一句都匹配不上——所以匹配不上的时候会走 `diagnose_block()`：截图 + 页面文字
交给模型，让它回答挡路的是验证码、登录墙、录像已过期，还是别的。实测在 bilibili 的
404 页和登录页上分别判成 `unavailable` 和 `login`，而关键词清单两个都没认出来。
「录像已过期」这种点一万次也没用的，直接停；验证码/登录墙才叫人。

**Q: 窗口编号从 #131 开始，是漏了前面 130 个吗？**
不是，那是旧版本把**归档流水号**当成窗口号显示了——`audit_records.jsonl` 里的 `id` 累计
所有历史运行。现在显示的是本次运行的窗口序号，从 #1 开始。

**Q: 报告里的时间和大屏对不上？**
报告只统计**本次运行**的结果；`audit_records.jsonl` 是跨所有运行的归档，两者不是一回事。大屏默认也只显示本次运行（见 `MONITOR_REPLAY_HISTORY`）。表格里的「定位」是视频绝对时间轴上的位置，不是片段内偏移。

**Q: 违规判得太松/太紧？**
改所用 YAML 的 `positive_indicators` / `negative_indicators`。注意 `absence` 类规则要求整个窗口都没观察到才判违规，观察不全一律 `CANNOT_DETERMINE`——这是刻意的，宁可漏报也不要一个不可复核的结论。
